# Модели бизнес-процесса

Нотация: BPMN-подобная модель с пулами и дорожками (пулы — участники процесса, прямоугольники — задачи, ромбы — шлюзы, толстые полосы — параллельное ветвление). Исходные тексты: `src-puml/as-is.puml`, `src-puml/to-be.puml`.

## Процесс «как есть»

![Процесс как есть](as-is.png)

Проверка назначенного наказания сегодня распределена между судьей и его помощником и целиком опирается на ручные операции.

Последовательность: судья изучает материалы, определяет квалификацию и формирует проект приговора. Помощник открывает текст УК РФ, находит санкцию нужной части статьи и вручную проверяет применимые правила Общей части — снижение верхнего предела при особом порядке, при досудебном соглашении, при неоконченном преступлении, при несовершеннолетии. Дальше следует шлюз: если у судьи возникает сомнение в размере наказания, помощник ищет похожие приговоры в открытых источниках по ключевым словам, прочитывает от пяти до пятнадцати актов и оценивает «на глаз», выбивается ли назначенное наказание из практики. Если сомнения нет, сравнение с практикой не выполняется вообще. При корректировке срока весь цикл проверки повторяется вручную.

**Узкие места, зафиксированные моделью**

| Узкое место | Следствие |
|---|---|
| Проверка правил Общей части выполняется вручную | Арифметическая ошибка при наложении нескольких коэффициентов не обнаруживается |
| Сравнение с практикой запускается по усмотрению, а не всегда | Систематическое отклонение от практики остается незамеченным |
| Выборка практики — 5-15 актов, найденных по ключевым словам | Нерепрезентативность и низкая точность подбора |
| Обоснование выбора срока нигде не фиксируется | Невозможно воспроизвести логику решения задним числом |
| Обратная связь наступает в апелляции | Ошибка выявляется через месяцы после оглашения |
| Повторная проверка после изменения срока — заново вручную | Судья избегает перебора вариантов из-за трудоемкости |

## Процесс «как будет»

![Процесс как будет](to-be.png)

В модели появляется третий пул — информационная система, и часть задач переносится в него.

Судья загружает проект приговора. Система извлекает параметры дела (ML: извлечение сущностей) и показывает их с оценкой достоверности. Шлюз проверки параметров остается за человеком: судья подтверждает или исправляет извлеченные значения — это сознательное требование, а не недоработка автоматизации. Затем система параллельно выполняет две ветви: детерминированную проверку санкции и правил Общей части и подбор сопоставимых приговоров с расчетом распределения сроков. Результат сводится в вердикты и справочное заключение. Если есть критичное отклонение, судья меняет срок прямо в системе и получает мгновенный пересчет — цикл, который в процессе «как есть» требовал повторной ручной проверки.

**Что именно меняет система**

| Элемент процесса | Было | Стало |
|---|---|---|
| Проверка Общей части | Ручная сверка по тексту кодекса | Автоматическая, полная, с указанием нормы и расчета |
| Сравнение с практикой | Выборочно, по 5-15 актам | Всегда, по всему корпусу, с показателем сходства |
| Оценка отклонения | Экспертное суждение «на глаз» | Количественная: положение в распределении сроков |
| Цикл «изменил срок — увидел результат» | Часы, повторная ручная проверка | Секунды, автоматический пересчет |
| Фиксация обоснования | Отсутствует | Заключение в архиве, воспроизводимое по версии модели и редакции справочника |
| Момент обратной связи | Апелляция, месяцы | До оглашения приговора |
| Роль помощника судьи | Основной исполнитель ручных проверок | Контроль параметров и работа с практикой |

Существенно, что процесс «как будет» не убирает ни одного решения судьи: система добавляет проверки и справочную информацию, но точки принятия решения (подтверждение параметров, выбор срока, оглашение приговора) остаются в пуле судьи.
