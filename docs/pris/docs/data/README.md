# Структура данных

Нотация: ER-диаграмма в нотации «вороньи лапки». Исходный текст: `src-puml/er.puml`.

![Структура данных](er.png)

## Группы сущностей

Модель делится на четыре группы, которые физически размещаются в разных хранилищах (обоснование — в [docs/architecture](../architecture/README.md)).

**Проверяемое дело** — `cases`, `case_documents`, `extracted_fields`, `punishments`. Дело создается из загруженного документа; каждый извлеченный параметр хранится отдельной записью с оценкой достоверности, ссылкой на фрагмент исходного текста, версией модели и признаком ручной корректировки. Такое решение принято сознательно: хранить параметры одной строкой в JSON было бы проще, но тогда невозможно измерить долю корректировок по каждому полю — ключевую метрику качества извлечения.

**Правовые справочники** — `sanction_rules`, `general_part_rules`. Санкция версионируется по датам действия редакции: проверка выполняется по редакции, действовавшей на дату деяния, а не на текущую дату. Правило Общей части хранит условие применимости и коэффициент, что позволяет добавлять новые правила без изменения кода.

**Результаты проверки** — `legal_checks`, `similar_sentences`, `predictions`, `reports`. Проверка ссылается на конкретную норму, по которой вынесен вердикт, и хранит расчетные пределы — без этого заключение невозможно объяснить. Прогнозы моделей сохраняются с именем и версией модели, что дает воспроизводимость: заключение годичной давности восстанавливается вместе с тем, какая версия его породила.

**Корпус приговоров** — `sentences`, `sentence_embeddings`, `courts`. Обезличенные приговоры с извлеченными признаками и векторными представлениями. Эмбеддинг вынесен в отдельную сущность, поскольку хранится в специализированной векторной базе, а не рядом с метаданными.

## Ключевые связи

| Связь | Кардинальность | Отношение |
|---|---|---|
| `cases` — `extracted_fields` | 1 : 0..* | Дело содержит ноль или несколько извлеченных параметров; параметр относится ровно к одному делу |
| `cases` — `legal_checks` | 1 : 0..* | Дело проходит одну или несколько правовых проверок; проверка выполняется ровно для одного дела |
| `sanction_rules` — `legal_checks` | 1 : 0..* | Санкция используется в ноле или нескольких проверках; проверка опирается не более чем на одну санкцию |
| `sentences` — `sentence_embeddings` | 1 : 1 | Приговор имеет ровно одно векторное представление; представление принадлежит ровно одному приговору |
| `cases` — `similar_sentences` — `sentences` | 1 : 0..* : 1 | Дело сопоставляется с несколькими приговорами; каждое сопоставление хранит показатель сходства и ранг |

## Решения, требующие пояснения

**Почему `extracted_fields` — отдельная таблица, а не колонки в `cases`.** Набор извлекаемых параметров меняется при развитии моделей, и добавление признака не должно требовать миграции схемы. Кроме того, у каждого поля есть собственные атрибуты — достоверность, фрагмент источника, версия модели, факт корректировки.

**Почему `punishments` хранит историю, а не текущее значение.** Судья меняет срок в ходе работы, и для анализа полезно знать, с какого значения начали и к какому пришли. Признак `is_current` выделяет актуальное наказание.

**Почему эмбеддинги отделены от `sentences`.** Вектор размерности 768 на пять миллионов документов — это данные, для которых нужен приближенный поиск ближайших соседей. Реляционная СУБД такой поиск не обеспечивает, поэтому вектор физически живет в специализированном хранилище, а в модели данных связь показана как 1:1.

**Почему нет персональных данных в корпусе.** `sentences` содержит только обезличенные признаки: статья, часть, дата, срок, вид наказания, обстоятельства. Исходные тексты хранятся в объектном хранилище отдельно и обезличиваются на этапе загрузки.
