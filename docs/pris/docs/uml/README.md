# UML-модели

Исходные тексты: `src-puml/components.puml`, `classes.puml`, `use-case.puml`, `sequence.puml`, `ml-pipeline.puml`.

## Структурные модели

### Диаграмма компонентов

![Диаграмма компонентов](components.png)

Диаграмма показывает разбиение на компоненты и интерфейсы между ними. Существенно, что `case-service` обращается к ML-компонентам и к правилам не напрямую, а через интерфейсы `IExtractor`, `IRuleEvaluator` и `ISimilaritySearch`. Это дает два практических следствия: модель извлечения заменяется новой версией без изменения кода дела, а на время пилота любой ML-компонент подменяется заглушкой на подготовленных данных — именно так работает текущий прототип, в котором извлечение имитируется.

Доступ к хранилищам изолирован адаптерами. Это не абстракция ради абстракции: в системе пять разнотипных хранилищ, и без разделения адаптеров сервисный код смешивал бы SQL, векторный поиск и объектный доступ.

### Диаграмма классов

![Диаграмма классов](classes.png)

Предметная модель построена вокруг двух агрегатов.

**`Case`** — корень агрегата проверяемого дела. Внутри: `ExtractedField` (извлеченный параметр с достоверностью), `Punishment` (наказание как value object), `ArticleRef` (квалификация), `LegalCheck` (результат проверки). Инварианты агрегата:

- изменение наказания инвалидирует все связанные проверки — они пересчитываются, а не остаются устаревшими;
- корректировка параметра судьей помечается признаком `isCorrected` и не перезаписывается последующим извлечением;
- вердикт не может существовать без ссылки на норму: `LegalCheck` всегда связан либо с `SanctionRule`, либо с `GeneralPartRule`.

**`Report`** — корень агрегата заключения. Заключение неизменяемо после формирования: повторная проверка создает новое заключение, а не меняет старое. Это требование воспроизводимости — архивное заключение должно отражать состояние на момент его выдачи.

`Sentence` и `SimilarSentence` относятся к корпусу практики и в агрегат дела не входят: они связываются с делом по ссылке, поскольку живут в другом хранилище и обновляются независимо.

## Поведенческие модели

### Диаграмма прецедентов

![Диаграмма прецедентов](use-case.png)

Четыре актора: судья (основной), помощник судьи (подмножество функций, без изменения срока и печати заключения), администратор (справочники и контроль качества моделей), конвейер загрузки корпуса (вторичный актор, инициирующий обновление базы приговоров).

Отношения: «Скорректировать параметр вручную» расширяет «Просмотреть извлеченные параметры» — корректировка нужна не всегда; «Изменить срок и пересчитать» расширяет «Проверить соответствие» по той же логике. Проверка соответствия и сравнение с практикой включают просмотр параметров, поскольку без подтвержденных параметров запускать их бессмысленно; печать включает формирование заключения.

Границей системы сознательно не охвачено вынесение приговора: это действие судьи вне системы.

### Диаграмма последовательности

![Диаграмма последовательности](sequence.png)

Диаграмма отражает полный цикл проверки — от загрузки документа до печати заключения — и показывает три момента, существенных для архитектуры.

Первый: извлечение параметров и их подтверждение разделены. Система не переходит к проверке автоматически; фрагмент `opt` показывает возможность ручной корректировки, и только после этого запускается проверка.

Второй: проверка выполняется тремя независимыми сервисами — правила, поиск аналогов, статистика. Они обращаются к разным хранилищам (PostgreSQL, векторный индекс, витрина), что на диаграмме видно по линиям жизни хранилищ.

Третий: фрагмент `loop` показывает живой пересчет. При изменении срока заново вызываются только правила и статистика; повторное извлечение параметров и повторный поиск аналогов не выполняются, поскольку набор сопоставимых дел от срока не зависит. Это решение дает требуемые 2 секунды на пересчет.

### Конвейер подготовки данных и обновления моделей

![Конвейер подготовки данных](ml-pipeline.png)

Диаграмма деятельности описывает работу дата-инженерной части: выгрузку приговоров и текстов закона, дедупликацию, обезличивание, разбор структуры акта, формирование признаков, параллельное обучение трех моделей и оценку на отложенной выборке.

Два момента зафиксированы в модели намеренно. Первый — шлюз после разбора структуры: акты, которые не удалось разобрать автоматически, отправляются в очередь ручной разметки, а не отбрасываются, поскольку именно они дают материал для улучшения модели. Второй — двухступенчатый контроль перед выводом версии модели в эксплуатацию: сначала сравнение метрик с текущей версией, затем теневой запуск на части трафика с проверкой расхождения. Модель, улучшившая метрики на отложенной выборке, но расходящаяся с текущей на реальном потоке, откатывается.
