# Архитектура системы

Исходный текст: `src-puml/architecture.puml`.

![Архитектура системы](architecture.png)

## Слои

**Клиентский слой.** Веб-интерфейс на Next.js 15 и React 19, состояние на Zustand, графики распределений на Recharts, шрифты ParaType. Интерфейс на русском языке, оформление в стиле судебных информационных систем.

**Слой приложений.** Семь сервисов с разделением по ответственности:

| Сервис | Ответственность | Владеемые данные |
|---|---|---|
| `api-gateway` | Аутентификация, маршрутизация, ограничение частоты | — |
| `case-service` | Жизненный цикл дела, параметры, архив заключений | `cases`, `extracted_fields`, `punishments` |
| `rules-engine` | Проверка санкции и правил Общей части, детерминированно | `sanction_rules`, `general_part_rules`, `legal_checks` |
| `extraction-service` | Извлечение параметров из документа (ML) | `predictions` (часть) |
| `similarity-service` | Подбор сопоставимых приговоров (ML) | `similar_sentences` |
| `statistics-service` | Распределения сроков, отклонение от медианы | витрина распределений |
| `report-service` | Формирование и хранение заключений | `reports` |

**Слой данных.** Пять хранилищ разного типа — см. раздел «Почему хранение распределенное».

**Конвейер загрузки корпуса.** `ingestion-pipeline` собирает акты из внешних источников, обезличивает, разбирает структуру, формирует признаки и эмбеддинги, наполняет все производные хранилища. `model-registry` хранит версии моделей с метриками и обеспечивает воспроизводимость заключений.

## Ключевое архитектурное решение: разделение правовой проверки и ML

`rules-engine` не содержит моделей машинного обучения и работает исключительно по справочникам. Его вердикт всегда сопровождается ссылкой на норму и расчетом пределов, поэтому воспроизводим и проверяем вручную. ML-сервисы поставляют вход для проверки (параметры дела) и контекст для сравнения (аналоги и статистика), но не участвуют в вынесении вердикта о соответствии закону.

Альтернатива — обучить модель предсказывать вердикт напрямую — технически проще и дала бы сопоставимую точность, но нарушила бы требование объяснимости: судья не может опираться на вывод, который нельзя проверить по тексту кодекса.

## Почему работа с данными носит распределенный характер

| Хранилище | Данные | Профиль доступа | Почему не PostgreSQL |
|---|---|---|---|
| PostgreSQL | Дела, параметры, проверки, пользователи, справочники | Транзакционный, строгая схема, целостность | — (это и есть основное OLTP-хранилище) |
| Qdrant | Эмбеддинги приговоров, до 5 млн векторов размерности 768 | Приближенный поиск ближайших соседей, top-20 за десятки миллисекунд | Реляционная СУБД не дает ANN-поиска на таком объеме за приемлемое время |
| OpenSearch | Полнотекстовый индекс текстов приговоров | Поиск по цитате и формулировке, фильтры по атрибутам | Полнотекстовый поиск в OLTP-СУБД по миллионам документов слишком медленный |
| ClickHouse | Витрина распределений сроков по статьям и признакам | Аналитические агрегаты, расчет квантилей | Расчет квантилей по десяткам миллионов строк в OLTP занимал бы секунды на каждый запрос |
| S3 (MinIO) | Исходные документы, тексты приговоров, PDF заключений | Объектный доступ, файлы до десятков мегабайт | Хранение бинарных файлов в СУБД недопустимо по объему и стоимости резервного копирования |

Помимо технических причин распределенность обоснована тремя организационными:

1. **Разные режимы обновления.** Дела меняются интерактивно, корпус обновляется пакетно раз в сутки, витрина пересчитывается по расписанию. В одном хранилище пакетная загрузка миллиона документов конкурировала бы за ресурсы с работой судьи.
2. **Разграничение персональных данных.** Загруженные проекты приговоров содержат персональные данные и остаются в контуре суда; обезличенный корпус их не содержит. Физическое разделение хранилищ обеспечивает это разграничение надежнее, чем права доступа внутри одной базы.
3. **Разная цена потери.** Векторный индекс восстанавливается пересчетом из корпуса за часы, и его потеря некритична. Потеря архива заключений недопустима. Это оправдывает разные стратегии резервного копирования.

**Согласованность.** Источник истины для корпуса — объектное хранилище с исходными текстами. PostgreSQL, векторный и полнотекстовый индексы, витрина — производные представления, восстанавливаемые пересчетом. Между ними допускается отложенная согласованность: расхождение на время пакетной загрузки не нарушает работу системы, а несогласованность разрешается повторным построением производных.
